# Private Profile Design

## Status

Design target only. This document does not change the installer, rebuild path,
public modules, or any existing `~/dotfiles-private` repository.

The product contract in [`PRODUCT.md`](./PRODUCT.md) is the authority for this
design.

## What the current private profile gets right

The committed private profile already has the correct ownership boundary:

```nix
inputs.dotfiles.url = "github:ucod3/dotfiles";
```

The private flake pins the public framework through `flake.lock`, while host
identity, application choices, preferences, and adopted files remain private.
Updating the framework therefore does not need to rewrite personal choices.

The current profile also keeps adopted files in the private repository and uses
Home Manager to deploy them.

These ideas stay.

## Current usability problems

The current profile is difficult to understand without prior knowledge of the
framework:

- `settings.nix` owns applications, AI integration, Homebrew cleanup, macOS
  defaults, and the example Home Manager profile.
- The public framework reads that file indirectly through a `.local` symlink and
  an impure loader rather than the private flake importing its own configuration.
- `home.nix` is generated by `dot adopt`, but appears beside hand-edited files
  without a repository-level guide explaining ownership.
- Host wiring, Home Manager wiring, user identity, application data, and adopted
  files use different conventions.
- Legacy folders can remain after their original mechanism has been removed,
  making it unclear whether they still affect the system.
- Custom commands hide several native Nix and Git operations instead of helping
  the user learn them.

The number of files is not the problem. The problem is that file responsibility
and data flow are not obvious.

## Design goals

A person opening `~/dotfiles-private` should be able to answer immediately:

1. Where do I add or remove an application?
2. Where do I change a macOS preference?
3. Which file represents this Mac?
4. Which files were generated?
5. Which files may I edit manually?
6. How is the public framework updated?
7. What must be pushed to restore this setup on another Mac?

The private profile must remain ordinary Nix. It must not introduce a custom
configuration language or require the `dot` CLI to remain understandable.

## Target structure

```text
~/dotfiles-private/
├── README.md
├── flake.nix
├── flake.lock
├── identity.nix
│
├── hosts/
│   └── <hostname>.nix
│
├── apps/
│   ├── default.nix
│   ├── homebrew-casks.nix
│   ├── nix-packages.nix
│   └── mac-app-store.nix
│
├── macos/
│   └── default.nix
│
└── home/
    ├── default.nix
    └── files/
        └── ...
```

This is a responsibility map, not a file-count target. A category should split
further only when it becomes difficult to scan or has an independent reason to
change.

## File responsibilities

### `README.md`

Generated with the private profile and written for its owner. It explains:

- the purpose of every top-level file and directory
- the normal edit → check → rebuild workflow
- the native Nix commands behind each convenience command
- how to update the public framework
- how to push the private profile safely
- how to restore it on another Mac
- which files are generated and should not be edited directly

### `flake.nix`

Small composition glue. It:

- consumes `github:ucod3/dotfiles` by default
- follows the framework's Nix inputs
- discovers or declares hosts
- imports the matching private host module

A custom framework fork is an explicit advanced override, not an installation
requirement.

### `flake.lock`

Generated by Nix. It records the exact framework revision and dependency graph.
The README explains that users update it with:

```bash
nix flake update dotfiles
```

### `identity.nix`

Contains private user identity used by Git and related tools. It is separate
from machine identity because one person may restore the same profile to more
than one Mac.

### `hosts/<hostname>.nix`

Contains only machine-specific composition and overrides:

- macOS username and hostname
- architecture when needed
- imports of `../apps`, `../macos`, and the shared public modules
- Home Manager imports of the public home environment and `../home`
- genuinely host-specific additions or overrides

It must not become a second general settings file.

### `apps/homebrew-casks.nix`

A plain list of GUI application cask names:

```nix
[
  "firefox"
  "ghostty"
  "rectangle"
]
```

### `apps/nix-packages.nix`

A normal Nix function returning packages:

```nix
{ pkgs }:
[
  pkgs.gh
  pkgs.jq
  pkgs.ripgrep
]
```

This preserves package evaluation and autocomplete without converting Nix
package expressions into strings that require a custom resolver.

### `apps/mac-app-store.nix`

A plain attribute set:

```nix
{
  Notability = 360593530;
}
```

### `apps/default.nix`

Composition only. It imports the three data files and assigns them to standard
nix-darwin / nix-homebrew options. Application choices have one source of truth.
No generated `apps.nix`, text parser, or second merged list.

### `macos/default.nix`

Contains the owner's macOS preferences using standard nix-darwin options.
Initially this may remain one cohesive file. It may later import files such as
`dock.nix`, `finder.nix`, or `keyboard.nix` when that improves readability.

Destructive or strongly opinionated behavior remains explicit.

### `home/default.nix`

Home Manager mappings for adopted files and private Home Manager configuration.
`dot adopt` may insert mappings here, but the file remains readable and clearly
marks its generated section.

### `home/files/`

The stored copies of adopted files. Directory paths mirror their destinations
under `$HOME` where practical.

## Composition model

The private flake imports its own modules normally. The public framework does
not reach back into the private repository through `.local`, environment
variables, absolute-path reads, or impure evaluation.

Conceptually, a private host composes:

```nix
{
  imports = [
    inputs.dotfiles.darwinModules.coreSystem
    ../apps
    ../macos
  ];

  home-manager.users.${user}.imports = [
    inputs.dotfiles.darwinModules.homeEnvironment
    ../home
  ];
}
```

Exact module placement will be verified against nix-darwin and Home Manager
before implementation.

## CLI principles

Commands are optional conveniences over visible files and native operations.

For example, after adding an application, the CLI should report:

```text
Added "firefox" to:
  ~/dotfiles-private/apps/homebrew-casks.nix

Equivalent manual change:
  Add "firefox" to that Nix list.

Next:
  dot rebuild
```

A command must not require parsing arbitrary Nix, create a second source of
truth, or hide which repository and files changed.

## Framework update model

Ordinary users do not publish framework changes. Their update path is:

```bash
cd ~/dotfiles-private
nix flake update dotfiles
git diff -- flake.lock
# evaluate or build, then commit flake.lock
```

A thin command may guide this workflow, but it should print the native commands
and operate only on the private profile's lock file.

Framework contributors use a separate checkout or fork and normal Git / pull
request workflows. Testing a local framework checkout is an explicit advanced
operation and must not silently change the stable pin.

## Migration requirements

Existing private profiles must not be rewritten in place automatically.

### Phase A — inventory

Before moving anything:

- require a clean or deliberately reviewed Git state
- fetch and compare the private remote
- record the active host name
- evaluate which files are currently imported
- identify legacy files and directories by evidence, not filename assumptions
- verify that the current profile can evaluate or build

### Phase B — add the new structure beside the old

Create the new files on a migration branch in the private repository. Do not
remove `settings.nix`, `home.nix`, `.local`, or legacy directories yet.

### Phase C — migrate one responsibility at a time

Suggested order:

1. application lists
2. macOS preferences
3. Home Manager profile toggles and personal modules
4. adopted-file mappings
5. identity

After each category:

- evaluate the private flake
- confirm the resolved values match the old path
- commit the category separately

### Phase D — switch imports

Only after equivalent evaluation is proven, make the host import the new private
modules directly. Build without switching first, then perform a reviewed switch.

### Phase E — remove compatibility machinery

After the live profile works through normal imports:

- remove the `.local` symlink dependency
- remove the impure private-settings loader from the public framework
- remove environment forwarding and special detection used only by that loader
- remove duplicate app representations and the custom Nix-list parser
- remove legacy folders only after proving nothing imports them

### Phase F — clean-machine proof

Generate a new profile from scratch in a VM or throwaway macOS account and test
the complete product journey defined in `PRODUCT.md`.

## Safety boundaries

- Never modify the user's current private profile directly from the public repo.
- Never migrate on `main` in either repository.
- Never combine application migration with deletion of old files in one commit.
- Never enable Homebrew cleanup against an unverified application set.
- Never expose private repository content in public commits, tests, fixtures, or
  logs.
- Never treat a local Git repository on the same disk as a backup.

## First implementation slice

The first behavioral PR should affect **newly generated profiles only** and must
be reviewable without touching an existing machine:

1. add private-profile templates matching this structure
2. generate a private `README.md`
3. default the framework input to `github:ucod3/dotfiles`
4. retain an explicit option for a custom framework fork
5. add fixture-based tests for generated file contents and imports
6. leave the current `.local` compatibility path intact

Migration of an existing profile is a separate, private-repository change after
the generator design has passed review.
